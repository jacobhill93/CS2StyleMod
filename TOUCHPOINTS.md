# Touchpoints

Inventory of game internals each `GameAdapters/` adapter depends on. Updated
whenever an adapter is added or re-verified against a new game version. See
"Patch-day workflow" in [ARCHITECTURE.md](ARCHITECTURE.md).

| `CustomZones/GameAdapters/ZonePrefabCloner.cs` | CustomZones | `Game.Prefabs.PrefabSystem.AddPrefab`, `Game.Prefabs.PrefabBase.Clone`, `Game.Prefabs.ZonePrefab`, `Game.Prefabs.UIObject.m_Group` | Cloning a `ZonePrefab` + `AddPrefab` registers a real, independent zone type and fully initializes on its own, **provided `AddPrefab` is called from `CustomZoneBuildRequestSystem`'s `OnUpdate`** (see that system's row below) - calling it from `OnGameLoaded` or any other arbitrary call site silently never initializes. | **In-game confirmed end-to-end**: visible, named, correctly colored, paintable, Steam build 25127643, 2026-10-08 |
| `CustomZones/GameAdapters/SpawnableBuildingZoneLinker.cs` | CustomZones | `Game.Prefabs.SpawnableBuilding.m_ZoneType`, `Game.Prefabs.BuildingSpawnGroupData`, `Game.Simulation.ZoneSpawnSystem.SelectBuilding`, `Game.Simulation.BuildingUpkeepSystem.SelectSpawnableBuilding` | Repointing `SpawnableBuilding.m_ZoneType` before registering is sufficient for both spawn and level-up selection to only offer that building on the target zone - neither Burst-compiled system needs patching, and `BuildingSpawnGroupData` gets set by the real `BuildingInitializeSystem` with no manual step, same timing requirement as above. | **In-game confirmed end-to-end**: spawns correctly, positioned correctly, survives construction, Steam build 25127643, 2026-10-08 |
| `CustomZones/CustomZoneBuildRequestSystem.cs` | CustomZones | `Game.Prefabs.PrefabSystem.OnUpdate` (drives `SystemUpdatePhase.PrefabUpdate`), `Game.Serialization.LoadGameSystem` (dispatches `OnGameLoaded`), `Game.Common.SystemOrder` (registration order within `MainLoop`), `Game.Common.PrepareCleanUpSystem`/`CleanUpSystem` (strip `Created`/`Updated` every frame) | **Root cause found (2026-10-08)**, see DECISIONS.md "A runtime-cloned prefab is only visible to init systems for one frame": `Created`/`Updated` live for exactly one frame, and `LoadGameSystem` (which dispatches `OnGameLoaded`) is registered *after* `PrefabSystem` in the same `MainLoop` phase - so a clone added from `OnGameLoaded` always misses that frame's one `PrefabUpdate` pass and gets its tags stripped before the next one. Fix: this system registers `UpdateBefore<_, PrefabSystem>(MainLoop)` (same registration DillonN/specialized-industrial-zones uses) and only ever calls `CustomZoneBuilder.BuildOrRebuild` from its own `OnUpdate`, via a pending-request queue (a `CustomZoneDefinition` + its resolved `Collection`s) any caller can enqueue into from anywhere. Supersedes and replaces the deleted `ManualPrefabInitializationWorkaround.cs`, which worked around the *symptoms* (missing geometry/`SubMesh`/`SubObject`/`BuildingSpawnGroupData`, manual `ZoneSystem` registry/color reflection) without knowing the cause. | **In-game confirmed**: identical results to the old workaround (zone gets a real `ZoneType` index, correct color/paint, building geometry/`SubMesh`/`SubObject`/`BuildingSpawnGroupData` all populated by the real systems) across a single-building experiment, the full ~416-building production path, and the rebuild (additive-clone/retire) path, zero manual reinitialization, Steam build 25127643, 2026-10-08 |
| `CustomZones/GameAdapters/GameBuildingCatalog.cs` | CustomZones | `Game.Prefabs.SpawnableBuildingData`, `Game.Prefabs.SignatureBuildingData`, `Game.Prefabs.BuildingData.m_LotSize`, `Game.Buildings.PropertyUtils.GetZoneDensity`, `Game.Zones.AreaType`, `Game.Prefabs.PrefabSystem.TryGetPrefab(Entity, out T)` | Real `Core.IBuildingCatalog`. Finds buildings by iterating an `EntityQuery` + matching `PrefabBase.name`, not `TryGetPrefab(PrefabID, out _)` - that overload's equality includes a content hash from the prefab's asset GUID, unknowable from a name alone, so it would never match. The `AreaType`/`IsOffice`/`ZoneDensity` → `Core.ZoneType` mapping mirrors ZoneOrganizer's own `IndexZones` categorization, not an assumption invented here. Excludes Signature buildings (`SignatureBuildingData` present) - they pass the `SpawnableBuildingData` query but are one-per-city landmarks, not regular growables; see DECISIONS.md. Also exposes `FindBuildingsByNamePrefix`, used by `CustomZoneBuilder`'s rebuild path to find what it already cloned for a zone. **Known incomplete**: `BuildingCandidate.AssetPackId` is always `null` - asset-pack-filtered `VanillaSelectorEntry`s currently match nothing; needs reading the building's `AssetPackElement` buffer. | **In-game confirmed**: resolves ~416 buildings correctly (12 Signature buildings now correctly excluded, not just failing to clone), used via `CustomZoneBuilder` with real `Collection` data, Steam build 25127643, 2026-10-08 |
| `CustomZones/GameAdapters/GameZonePrefabResolver.cs` | CustomZones | `Game.Prefabs.ZoneData`, `Game.Prefabs.ZonePropertiesData`, `Game.Prefabs.PrefabSystem.TryGetPrefab(Entity, out T)` | Resolves `ZonePrefab`s two ways: a vanilla zone matching a `Core.ZoneType` category (reuses `GameBuildingCatalog.TryMapToCoreZoneType`, made `internal` rather than duplicated), or an already-registered zone by exact name (same name-match technique as `GameBuildingCatalog.TryGetBuildingPrefab`) - the second is what lets `CustomZoneBuilder` find a zone it already built, for rebuild. | **In-game confirmed**: both lookups work correctly across the build and rebuild paths, Steam build 25127643, 2026-10-08 |
